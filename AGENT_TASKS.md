# Веб-приложение: общий бриф для код-агента

Реализуй всё нижеперечисленное **по фазам, сверху вниз**. Фаза 0 — критическая
(безопасность), её делаем до всего остального. Внутри фазы — один коммит на блок,
после каждого блока: `python3 -m py_compile api/main.py` и `node --check web/app.js`
(плюс `pytest -q`, где есть тесты), затем `git push origin main`.

## Общие правила
- Бизнес-логику держим в общем слое `app/`, веб (`api/`, `web/`) — тонкий. Не
  дублируй уже существующие функции бота — переиспользуй.
- Не вписывай секреты в код. Новые env-переменные — только читать из окружения,
  значения задаёт пользователь в Coolify.
- Ничего из существующего не ломаем; все изменения обратносовместимы.
- Веб делаем «на максималках»: бот = быстрый захват, веб = планирование, обзор,
  отчёты, фото, графики, админка. Где носитель выигрывает — делаем богато.
- Каждое необратимое действие в UI — через подтверждение.

## ФАЗА 0 — КРИТИЧЕСКАЯ БЕЗОПАСНОСТЬ (сделать первой)

### 0.1 IDOR: скоупить все обращения по {id} по владельцу (uid)
Сейчас объекты достаются только по id, без проверки владельца. Любой
аутентифицированный пользователь может читать/менять/удалять чужие данные,
перебирая числовые id. Это боевая дыра, как только в системе >1 пользователя.

Затронутые эндпоинты в `api/main.py` (проверить и закрыть КАЖДЫЙ):
- `GET /api/workouts/{wid}`, `PATCH /api/workouts/{wid}/notes`,
  `DELETE /api/workouts/{wid}`, `POST /api/workouts/{wid}/finish`,
  `POST /api/workouts/{wid}/sets`
- `PATCH /api/sets/{sid}`, `DELETE /api/sets/{sid}`
- `GET /api/plans/{pid}`, `PATCH /api/plans/{pid}`, `DELETE /api/plans/{pid}`
- `DELETE /api/measurements/{mid}`

Подход (выбери единообразно):
- Добавь в `app/db` проверку владельца: либо новые функции с `user_id` в WHERE,
  либо хелперы `assert_owns_workout(uid, wid)`, `assert_owns_plan(uid, pid)`,
  `assert_owns_set(uid, sid)`, `assert_owns_measurement(uid, mid)`. Для set —
  владелец определяется через `workouts.user_id` его тренировки.
- В каждом эндпоинте: загрузил объект → если `user_id != uid` (или не найдено) →
  `raise HTTPException(404, "not found")` (404, не 403 — не палим существование).
Acceptance: запрос к чужому id отдаёт 404 на чтение и на мутации.

### 0.2 Хард-фейл небезопасного секрета в проде
В `api/auth.py`/старте приложения: если `APP_ENV=production` и `SESSION_SECRET`
пуст или равен `dev-insecure-secret-change-me` — падать на старте с понятной
ошибкой. То же для пустого `TELEGRAM_BOT_TOKEN` в проде.

## ФАЗА 1 — КОРРЕКТНОСТЬ И АРЕНДНОСТЬ

### 1.1 Часовой пояс в датовой логике веба
Веб использует `date.today()` (UTC контейнера) в ~12 местах; бот считает
per-user через `app.bot.services.tz.today(uid)`. Из-за этого «сегодня»/«план на
сегодня» едут для пользователей не в UTC.
- Заведи `async def today_for(uid)` (обёртка над `await tz.today(uid)`) и замени
  им все `date.today()` в пользовательских эндпоинтах (dashboard, `/plans`,
  `create_workout`, finish, сравнения и т.п.).
Acceptance: для uid с TZ Europe/Moscow поздним вечером «сегодня» = локальная дата.

### 1.2 Экранирование пользовательского текста в вебе (XSS)
В `web/app.js` весь пользовательский текст, попадающий в `innerHTML`
(`focus_label`, заметки, имена упражнений, display_name и т.п.), оборачивать в
существующую `esc()`. Пройти все шаблоны и закрыть пропуски.
Acceptance: тренировка с названием `<img src=x onerror=alert(1)>` отображается
как текст, код не исполняется.

### 1.3 Очистка AI-кэша упражнений — только админ
`wipe_exercise_aliases()` глобальна (общая для всех). Перенести пункт «Очистить
AI-кэш упражнений» из общих Настроек в админ-раздел за проверку `is_admin`
(эндпоинт и кнопка видны только админам).

### 1.4 Валидация формы плановых упражнений
Формализуй shape в `_clean_plan_exercises` (или рядом): отбрасывай мусорные
поля, валидируй типы (sets/reps — int|None, weight — float|None), на грубо
кривой вход — 422. JSONB-хранение оставляем.

## ФАЗА 2 — ЛИМИТЫ НА AI (ключ есть, нужен ограничитель)

Перед любым AI-вызовом (разбор плана `/plans/parse`, коуч, vision по фото,
транскрипция голоса) — лимит на пользователя.
- Таблица `ai_usage(uid TEXT, day DATE, count INT, PRIMARY KEY(uid, day))` в
  `api/schema.py`. Хелпер `async def check_and_bump_ai(uid, limit=<env AI_DAILY_LIMIT, default 100>)`:
  атомарно `INSERT ... ON CONFLICT DO UPDATE SET count=count+1 RETURNING count`;
  если превышен — `raise HTTPException(429, "дневной лимит AI исчерпан")`.
- Применить во всех AI-эндпоинтах. (Если позже поднимешь Redis — токен-бакет
  чище, но БД-счётчика достаточно.)

## ФАЗА 3 — ФИЧИ ВЕБА «НА МАКСИМАЛКАХ»

### 3.1 AI-коуч (разбор тренировки)
Готово: `app.bot.services.coach.build_coach_facts(uid, workout_id)`,
`opus_coach_summary(facts)`.
- `GET /api/workouts/{wid}/coach` (за current_uid, с проверкой владельца и
  AI-лимитом) → `{summary, facts}`.
- Фронт: на финишном sheet кнопка «🤖 AI-разбор» со спиннером → показывает текст.

### 3.2 AI-нормализация имён упражнений (самообучение)
Готово: `app.bot.services.exercise_catalog.resolve_or_register(name)` →
`{canonical, muscle_group, source}`, кэширует в общей `exercise_aliases`.
- Применять на бэке, где приходит произвольное имя: при логе подхода с
  `exercise_name` (не из каталога) и при сохранении планов — нормализовать
  через `resolve_or_register` (под AI-лимит). Любая ошибка → fallback на
  исходное имя, не блокировать сохранение.

### 3.3 Часовой пояс по геолокации
Готово: `tz.tz_from_coords(lat, lon)`, `tz.set_user_tz(uid, name)`.
- `POST /api/service/tz/coords {lat,lon}` → имя зоны или 422; set + вернуть.
- Фронт (Настройки): кнопка «📍 Поделиться геолокацией» →
  `navigator.geolocation.getCurrentPosition` → POST → обновить пояс.

### 3.4 Отчёты (PDF за период)
Готово: `app.bot.services.report_builder.build_period_report(...)` (проверь
сигнатуру; возвращает PDF-байты).
- `GET /api/reports?days=7|14|30|60` и `GET /api/reports?from=YYYY-MM-DD&to=...`
  (за current_uid) → стрим PDF (`application/pdf`, Content-Disposition
  attachment). Под AI-лимит, если внутри есть AI.
- Фронт: экран «Отчёты» (пресеты 1/2 недели, месяц, 2 месяца + произвольный
  период) → скачивание/открытие PDF.
- Для веб-фото (фаза 3.6) отчёт берёт картинки из локального хранилища, когда
  `telegram_file_id` пуст.

### 3.5 Голосовой ввод
Готово: `app.bot.services.ai_parser.transcribe_voice(bytes, filename)` (Whisper).
- `POST /api/voice/transcribe` (multipart audio, за current_uid, AI-лимит) →
  `{text}`. Дальше текст идёт в существующие парсеры подходов/замеров.
- Фронт: кнопка-микрофон в добавлении подхода и в замерах → запись через
  `MediaRecorder` (webm/opus) → upload → подставить распознанный текст в поле.

### 3.6 Прогресс-фото (хранение на сервере)
Готово: `app.bot.services.photo_vision.describe_photo_series(images)`,
`report_builder._resize_photo`, таблица `progress_photos`, функции серий в
`app/db`.
- Хранение: persistent volume на сервере (путь из env `PHOTO_DIR`, напр.
  `/data/photos`). В `progress_photos` сделать `telegram_file_id` nullable,
  добавить `storage_key TEXT` (имя файла на диске).
- `POST /api/photos` (multipart 1..N фото, AI-лимит): ресайз (`_resize_photo`) →
  сохранить на диск → один `series_id` на загрузку → `describe_photo_series`
  по байтам → сохранить short/detailed описание → опциональный текст-коммент.
- `GET /api/photos` (серии, пагинация), `GET /api/photos/{id}/image` (стрим с
  диска, проверка владельца), `DELETE /api/photos/series/{sid}` (владелец).
- Фронт: экран «Фото» — загрузка, превью серии, AI-описание, история, удаление.
  Заменить заглушку «Фото — в следующей версии» на «Главной».

## ФАЗА 4 — ОФЛАЙН-ОСНОВА (заложить сразу, под будущее офлайн-приложение)
Цель: активная тренировка работает при плохой/отсутствующей сети.
- Service worker: оболочка уже кэшируется; добавить надёжную выдачу оболочки
  офлайн (уже network-first — оставить, API не кэшировать).
- IndexedDB-очередь для логирования подходов активной тренировки:
  при офлайне/ошибке POST — класть подход в очередь с временным id, показывать
  оптимистично; при возврате сети (`online`/Background Sync) — досылать по
  порядку, идемпотентно (клиентский `client_op_id`, сервер игнорирует дубли).
- Локально кэшировать состояние активной тренировки, чтобы таймеры и список
  подходов жили без сети.
Делать только для flow активной тренировки (подходы/таймеры) — там основная
ценность; остальное приложение пока online.
